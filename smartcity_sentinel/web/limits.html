What this can't do (yet).

Every result has a boundary. Here is what the running code actually does, and what would have to change before we could make a bigger claim.

CLAIMWHAT ACTUALLY HAPPENSWHAT IT WOULD TAKE

Traffic forecast

A traffic forecast could tell us what comes next.

The API calls forecast_traffic_baseline, a small trend heuristic. No trainable LSTM implementation is connected in this build.

Collect real traffic history, implement and train a forecast model, then evaluate it against held-out periods and a simple baseline.

Anomaly models

An anomaly score could identify a failing sensor.

The isolation forest and tiny autoencoder are fitted on the first 30 generated sensor rows. Their scores are not calibrated probabilities.

Gather representative fault and normal histories, validate thresholds with operators, measure false alarms, and recalibrate when conditions change.

All input data

The page can observe real cameras and infrastructure sensors.

Readings, alerts, and crowd points are generated by local code. No camera or live sensor is read.

Authorized device integrations, a data-quality plan, clear retention rules, and a way to test each feed without exposing sensitive data.

Live alert stream

Incoming alerts represent changing city conditions.

Every five seconds the API picks a generated template, changes its ID and timestamp, and varies severity slightly.

Connect verified event sources, preserve their provenance, and test that duplicate, delayed, or missing messages are handled safely.

Login and permissions

The role map controls who can use the API.

There is no login. role_allows checks a static example map, but the API does not call it for authentication.

Add an identity provider, enforce authorization on every route, review session handling, and keep the service behind a deliberate network boundary.

Saved state

Events and configuration will still be there after a restart.

The API keeps its working state in memory. Its startup demo files live in a temporary directory, so a restart begins a fresh run.

Choose durable storage, define backup and recovery behavior, and document which generated or operational records should survive.

Privacy noise

Every response protects individual records with noise.

Laplace noise is added to one demonstration count. Other API responses are not automatically privatized.

Set a system-wide privacy design, track repeated queries and sensitivity, and test the complete release path rather than one helper.

Audit chain

A hash chain prevents someone from changing the audit history.

HashChainAuditLog can detect an edit when it verifies the linked records. It cannot stop someone from replacing the whole file and chain.

Protect signing keys and storage separately, restrict write access, export checkpoints, and monitor copies held outside the machine.

Fairness sample

The group rates show whether a system is fair.

The audit counts false-positive and false-negative rates in a small bundled CSV. Groups under 30 rows are explicitly flagged.

Use a representative, consented evaluation set, define relevant harms with affected communities, and compare uncertainty as well as rates.

Federated averaging

Devices train a shared model without sharing local data.

FedAvg calculates a sample-count-weighted mean of the supplied numbers. It does not train a model or communicate with a device.

Implement local training, secure update exchange, aggregation rounds, and checks for poisoned or incompatible updates.

Optional vision and explanation code

YOLO, OCR, SHAP, and Grad-CAM all run in the demo.

Optional YOLO, EasyOCR, and SHAP adapters exist but are not wired into the demo. No Grad-CAM implementation was found in this build.

Install optional packages and local model files deliberately, connect tested inputs, and review each output before it affects an operation.

WHERE WE WOULD GO NEXT

Four pieces of evidence before a bigger claim.

  1. Measure first. Connect authorized sensor history and check its quality over time.
  2. Validate forecasts. Train against real history and compare results with a baseline on held-out periods.
  3. Protect access. Add authentication, route-level authorization, and a deliberate deployment boundary.
  4. Test harms. Evaluate privacy, model errors, and group differences with representative data and a clear review process.
